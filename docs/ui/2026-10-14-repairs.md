# Hero, photography and dashboard control repairs

The marketing script initialized products before its currency and locale variables.
Products with a positive free-shipping threshold called the price formatter during
that initialization, causing a JavaScript error before the hero controls and timers
started. Currency and locale now initialize first. Slider timing, hover/focus
pauses, reduced-motion behavior, arrows and dots retain their existing behavior.

The subsequent correction restores the original component-specific photo shapes.
Categories remain circular; product frames keep their rounded top edges; compact,
collection, journal, gallery, cart and checkout photos keep their own homepage
geometry. Photos inside clipped frames inherit the visible outer rounding where
needed. Only the small homepage promotional banners get larger corners: 32px
frames and 24px photos. Quantity badges remain unclipped. Logos, icons and circular
avatars keep their shapes. Dashboard photos retain their approved component CSS.

The subsequent correction removes the broad live button padding/height/wrapping
overrides. Buttons retain approved typography, corners, colors and spacing.
Mobile order-button grid positioning no longer leaks into reward, support-reply
or product-upload actions. CSRF form-wrapped notification buttons preserve their
link presentation and remain reachable on mobile; Clear Cart only adapts native
button text centering. These changes are scoped to live dashboards. Frozen
approved assets, palette, input styling and original layouts are unchanged.

## Seller access

New stores start as `pending_verification`. After the normal email/onboarding and
required MFA steps, their members can read their own Orders and Shipping pages
alongside the other 15 connected Seller destinations. A verification notice links
eligible store managers to the existing verification workflow. A pending store
does not advertise fulfilment controls or acquire approval from opening a page.

Processing, picking, packing, dispatch and external order API access, including
cached idempotency preflight, still require a verified store. Current identity,
session version, membership, store, country and record ownership checks remain.
Suspension blocks operational pages and writes while preserving the existing
read-only Store Settings page. Closed stores retain their existing access denial.

## Regression coverage

- `test/storefront-boot.test.js` executes actual shipping-price initialization for
  all five supported markets, with explicit and country-default currencies.
- `tests/e2e/marketing-motion.spec.js` checks rendered manual navigation, timer
  transitions, hover/focus, reduced motion and page suspension on desktop/mobile.
- `tests/e2e/image-corners.spec.js` checks actual photos, frames, gallery previews,
  cart/checkout badges, public journal/seller pages, and persisted Customer
  wishlist/comparison after refresh. The signup case requires
  `E2E_IMAGE_SIGNUP=true` on an isolated seeded simple-login test server.
- `test/dashboard-controls-live.test.js` uses real password/MFA sessions and
  current grants for eight connected workspaces. It visits canonical and personal
  account pages at 1366px, 390px and 320px, checking rendered label bounds, form
  layout, photo corners, browser errors and horizontal page overflow.
- `test/seller-pending-workspace-live.test.js` covers real signup, email
  verification, onboarding, MFA and later login; all 17 Seller destinations and
  aliases; scoped own/foreign orders; blocked pending writes/API; and suspension.
  Existing Seller order, store, overview and payment/API regressions also run.

Live Node tests require an isolated, transaction-capable loopback MongoDB URI in
`CLASSIC_MART_LIVE_TEST_MONGO_URI`. Run files serially with
`--test-concurrency=1 --import ./scripts/live-test-model-lifecycle.js`; use the
installed Chromium through `PLAYWRIGHT_CHROMIUM_EXECUTABLE` when needed. Local
fixture messaging uses logs. These checks do not establish live provider delivery,
production load certification or a complete production release gate.

The earlier checkpoint's targeted runs passed 84 test entries without failures or skips: 30 Seller
and storefront initialization entries, 25 approved UI/Customer/request contracts,
nine dashboard browser entries and 20 desktop/mobile hero/image cases. The
dashboard sweep checked 131 route/workspace pairs at three widths (393 visits)
and 1,326 rendered controls. A separate public-page sweep checked 24 routes at
three widths (72 visits), with no browser errors, clipped labels or page overflow.
Project/import, security, frontend and functionality gates passed; dependency
audit reported zero vulnerabilities. This is targeted repair verification, not
an assertion that the full production release gate has passed. The later cleanup
and visual restoration require their own current verification record; these older
counts do not certify the new changes.
